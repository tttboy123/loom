## Scope (three delivery boundaries)

### W1 — Product-line scheduling closure (real user journey)

The Queue / Workers / Integration screens in the real PTY TUI gain genuine
product operations (not just observation): create a Job into the Queue
(admission via the existing `queue_command create_job`), explicitly claim a
worker (`workers_command claim`), record a deterministic test result
(`workers_command result`), record a review verdict, and integrate / publish /
rollback (`integration_command integrate|adopt|rollback`). The production
native app observes the same projection through the production Swift client.
An end-to-end real GUI+TUI journey (alternative verification method) must
pass `freeze`/`verify` with the frozen evidence schema.

### W2 — Two real parallel development Candidates (self-host strongest proof)

Using the Loom scheduling flow itself, drive two genuinely parallel
development Candidates: two independent workers each claim one Job on a
separate Candidate branch/worktree, both clients observe the parallel
claims, a deterministic test result routes per the seven-class taxonomy, the
read-only Reviewer verdicts, and the single Integrator lands exactly one
versioned release — all recorded in the Event Journal and verified by the
dual-Result gate.

### W3 — Controlled self-host canary as a repeatable product function

locked runtime fixture, exact bindings, idempotent CAS, no duplicate
Run/Evidence/effect, no oversell, projection-failure preserves the old view,
crash recovery correct) and demonstrate it end to end on the v0.4.1 product.
