## 1. 背景与动机

### 1.1 v0.3 已建立的不变量（保留）

v0.3 阶段的 14 条不变量（见 `TECH-PLAN.md §1.1`）中，以下 9 条 v2.0 **继续保留**：

| # | 不变量 | v2.0 是否保留 | 理由 |
|---|---|---|---|
| 1 | 普通输入不自动创建 Agent 团队 | ✅ 保留 | 与 Multica 的"显式进入"一致 |
| 2 | 每团队有且只有一个 Main Agent | ✅ 保留 | Multica Squad leader 等价 |
| 3 | Main Agent 不直接承担交付物修改 | ✅ 保留 | Multica leader 只路由 |
| 4 | 模型生成团队必须用户确认 | ✅ 保留 | Multica 也是显式模式 |
| 5 | AgentDefinition / RuntimeProfile / RuntimeInstance 分离 | ✅ 保留 | 仍是 3 层抽象 |
| 6 | 执行 Agent 只能提交 `ready_for_review` | ✅ 保留 | Multica 同源 |
| 7 | `require_approval` 暂停工作项 | ✅ 保留 | 客户规则 |
| 9 | Event 追加写；看板可重建 | ✅ 保留 | 不变量 |
| 10 | Sidecar 不修改运行中团队 | ✅ 保留 | 不变量 |
| 11 | Team Draft 只引用真实可用项 | ✅ 保留 → 强化 | v2.0 引入 Skill，draft 校验更严 |
| 13 | Run 消息匹配 `claim_generation` | ✅ 保留 → 升级 | v2.0 引入 Daemon 轮询 + 3-token |
| 14 | terminal / Evidence 先本地 | ✅ 保留 | 不变量 |

**v0.3 中需要修改的 2 条**：

- **不变量 #8**（Loom 自签临时凭证）→ v2.0 拆为 **3 类 token**（User / Daemon / Run），各自签名 + 各自验证域
- **不变量 #12**（AgentGrant 任务级）→ v2.0 升级为 **RunToken**，域比 AgentGrant 更细：仅授予当前 Issue/Task 集合，不跨 Squad 共享

**v0.3 中**完全重写**的 2 条**：

- 不变量 #2 的"Main Agent"概念 → v2.0 引入 Squad 抽象，Main Agent = Squad leader
- 不变量 #11 的"目录快照" → v2.0 升级为 Skill Registry + Squad Definition 双源

### 1.2 为什么 pivot 到 Multica 全对齐

Multica 自 2026-01 公开，4 个月 2.7k stars，自述"非常接近 PMF"。在 6 个社区 audit（Anthropic / Swarms / aevatar / Multica / Omnigent / 自家 v1.1）中，Multica 是唯一一个在"团队组织层"上**端到端可工作**的开源项目。Loom v1.1 在"运行时层"（Linux 进程 + cgroup + OOM killer + 事件溯源）有原创性，但在"组织层"上必须承认 Multica 更成熟。

**v2.0 命题**：把 Multica 的 5 维组织层（Skill / Squad / 3rd-party CLI / 3-token / MCP）**完整复刻**到 Loom，保留 Loom 自己的运行时层（Go daemon + Linux 进程 + cgroup）。两者正交：Multica 是"如何组织 agent 团队"，Loom 是"如何安全地让 agent 跑在你机器上"。

### 1.3 v2.0 核心命题

```
v2.0 = Multica 组织层（Skill + Squad + 3rd-CLI + 3-token + MCP）
     + Loom 运行时层（Go daemon + Linux 进程 + cgroup + OOM）
     + AgentENV 沙箱层（Firecracker + overlaybd + <50ms 启停）
     + Multica 没有的本地化强化（凭证代理 + Sidecar + 显式批准）
```

### 1.4 与 Multica 刻意不同的边界（我们不改的）

Multica 是云优先 / Linear-style 团队 shell；Loom 不会复制这些：

1. **不做云端控制面**：Loom daemon 永远在用户本机；不引入 Loom Cloud 概念
2. **不做 Marketplace**：ClawHub 3rd-party Skill 是 ClawHavoc 事件的根因（2026-02）；v2.0 Skill 走 4 个导入源，**不允许用户上传不明 Skill** 到共享库
3. **不做 Web 控制台优先**：Loom 主入口是 CLI / TUI；Web 是可选 helper
4. **不做自动 fork 用户项目**：Multica 假设 daemon 永远在跑；Loom 允许 daemon 退出后 Run 暂停、重连后恢复
5. **不做 Provider 凭证进 daemon**：v0.3 不变量 #8 强化版 — Provider 凭证只经 Credential Broker，daemon 持有临时短寿命代理凭证

## 2. 5 维度设计

### 2.1 Skill 系统

#### 2.1.1 Skill 实体

```yaml
Skill:
  id: skl_<8hex>
  name: "string"                    # 唯一；如 "go-test-runner"
  version: "semver"                 # 强制 semver；首次发 0.1.0
  source: enum{registry, git, local, inline}
  source_ref: "string"              # registry 名 / git URL+rev / 本地路径 / 描述块
  description: "string"             # 一句话作用
  input_schema: JSONSchema          # 输入契约
  output_schema: JSONSchema         # 输出契约
  timeout_ms: int                   # 单次执行超时
  cost_budget_usd: float            # 单次调用成本上限
  side_effect: enum{none, fs, network, both}
  scope: enum{local, workspace, squad}   # ClawHavoc 防御：默认 local
  mounts: list[MountSpec]           # 显式挂载；空 = 沙箱内只读
  env_whitelist: list[string]       # 允许读取的环境变量名
  created_at: ISO8601
  updated_at: ISO8601
  hash: sha256                      # 内容寻址；变更即新版本
```

#### 2.1.2 4 个导入源（不允许第 5 个）

| Source | 信任域 | ClawHavoc 防御 |
|---|---|---|
| `registry` | Loom 官方 registry（v2.0 内置 ~10 个基础 Skill） | 签名验证 + 平台审计 |
| `git` | 用户指定的 git URL + rev | 必须固定 commit hash；首次拉取 sandbox 内 dry-run |
| `local` | 用户本地文件路径 | 必须在 Skill Registry 显式注册；只读挂载 |
| `inline` | 当前 Squad definition 内嵌的描述块 | 仅 squad 作用域；不持久化到全局 |

**ClawHavoc 三大防御（来自 2026-02 Multica 事件复盘）**：
1. `custom_env` 显式白名单（`env_whitelist`）— 不允许通配
2. `scope` 默认 `local`；升级到 `workspace` 或 `squad` 必须显式 + 写明警告
3. `mounts` 显式声明；空数组 = 沙箱内只读

#### 2.1.3 Skill 复用规则

- Squad 定义可引用任意已注册 Skill 的固定版本（`name@version`）
- Squad 实例化时复制 Skill 快照到 squad 私有注册表；后续 Skill 升级不影响在跑 Squad
- Skill `version` 必须 semver；自动 patch 升级可配（默认 off）
- 跨 Squad 共享 Skill 只在 `scope=squad` 允许；`scope=local` 不可跨 Squad

#### 2.1.4 与 v0.3 不变量 #11 的衔接

v0.3 的"Team Draft 只能引用目录快照中真实可用"升级为：

- Team Draft 引用 = Squad Definition 引用 = Squad 内每个 Agent 引用 = Agent 内的 Skill 列表引用
- 每一层都必须在 Snapshot 时验证：源可达、签名合法、hash 一致

### 2.2 Squad 多 Agent 路由

#### 2.2.1 Squad 实体

```yaml
Squad:
  id: sqd_<8hex>
  name: "string"                    # 用户命名
  leader: AgentRef                 # 唯一 leader（v0.3 不变量 #2）
  members: list[AgentRef]           # 含 leader
  skills: list[SkillRef@semver]
  routing_rules: list[RoutingRule]
  issue_policy: enum{one_to_one, one_to_many, fanout}
  archive_policy: enum{never, on_close, manual}
  max_concurrent_tasks: int         # default 6
  created_at, updated_at
```

#### 2.2.2 RoutingRule（Multica leader 协议移植）

```yaml
RoutingRule:
  trigger: enum{comment, issue_status, timer, signal}
  match: cel_expression             # 触发条件
  action: enum{assign, reassign, reply, archive, escalate}
  target: AgentRef | SquadRef
  prevent_self_loop: bool           # 默认 true
  anti_self_loop_scope: enum{turn, session, never}
```

**anti-self-loop 规则（来自 Multica v0.3.1）**：leader 自己的评论不触发自己的 routing rule。`prevent_self_loop=true` 时检查 `comment.author == squad.leader` 直接 return；这是 Multica 防止 token 死循环的核心。

#### 2.2.3 Squad 工作模式

| 模式 | 行为 | 适用 |
|---|---|---|
| `one_to_one` | 一个 Issue 一个 Task；简单协作 | 1 主 1 助 |
| `one_to_many` | 一个 Issue 拆 N 个 Task 并行 | review 类（reviewer A/B/C 并行审查） |
| `fanout` | N 个独立 Issue 并行处理 | 多客户端同时投递 |

#### 2.2.4 Squad 生命周期

```
Draft（未实例化）→ Active（接 Issue）→ Paused（暂停接收）→ Archived
                ↘ Destroyed（彻底删除，30 天后）
```

- `archive_policy=never`：从不归档
- `archive_policy=on_close`：所有 Task 终态后 7 天归档
- `archive_policy=manual`：用户显式归档

#### 2.2.5 Squad 与 v0.3 Team 的兼容

- v0.3 的 `TeamInstance` 是 Squad 的 `Active` 状态特例
- v0.3 的 `Team Draft` 是 Squad 的 `Draft` 状态
- v0.3 不变量 #2（每团队一个 Main Agent）= Squad 的 `leader` 字段
- v0.3 不变量 #3（Main Agent 不直接修改）= Squad leader 在 routing rule 中只允许 `assign/reassign/reply/archive/escalate` 五种 action，**不允许 `execute_task`**

### 2.4 3-Token 认证

#### 2.4.1 三类 Token 的域

| Token | 谁签发 | 谁验证 | 域 | 寿命 | 用途 |
|---|---|---|---|---|---|
| **UserToken** | Loom daemon（启动时） | Loom daemon | 用户全权限 | 会话级（daemon 在则有效） | 客户端调用 daemon 全部 API |
| **DaemonToken** | 3rd-party CLI 自身或 OAuth 提供商 | Loom daemon | 单 RuntimeInstance 权限 | RuntimeInstance 在线期间 | 3rd-party CLI 反向回调 Loom |
| **RunToken** | Loom daemon（dispatch 时） | Loom daemon | 单 Issue/Task 集合 | Task 终态后 5 分钟自动吊销 | Agent 进程调用 Loom 受限能力 |

**关键点**：v0.3 的 `AgentGrant` 被 v2.0 的 `RunToken` **完全取代**。AgentGrant 是静态签发 + 全局共享；RunToken 是 Issue-scoped + 5 分钟寿命 + 单向能力。

#### 2.4.2 凭证流（参考 Multica 三层）

```
User
  │ (1) 启动 daemon，daemon 从 Keychain 拉 Provider 凭证
  │     真实 Provider 凭证（OpenAI/Anthropic API key）永不出 daemon
  ▼
Loom Daemon
  │ (2) 持有 Provider 凭证（仅在内存 + mlock）
  │     持有 macOS Keychain 句柄
  ▼
3rd-party CLI 进程
  │ (3) 通过 DaemonToken 反向调用 daemon 受限 API
  │     daemon 验证 DaemonToken → 临时代理 Provider 凭证
  │     Provider 凭证绝不下发到 CLI 进程
  ▼
Agent 进程（在 3rd-party CLI 内的推理循环）
  │ (4) 通过 RunToken 调用 Loom 能力（提交 Evidence / 写状态 / 读 Issue）
  │     RunToken 不含 Provider 权限 — 绝不能冒充 Provider
```

#### 2.4.3 RunToken 详细设计

```yaml
RunToken:
  token_id: rt_<16hex>
  squad_id: sqd_<8hex>
  issue_ids: list[iid_<8hex>]          # 多 Issue 共享一个 Token（Squad 内部）
  task_ids: list[tid_<8hex>]           # 动态扩缩
  capabilities: list[Capability]       # 白名单；非默认全开
  issued_at: ISO8601
  expires_at: ISO8601                  # 默认 5min 后；最长 1h
  parent_generation: int               # 配合 v0.3 不变量 #13
  signature: ed25519                   # daemon 私钥签
```

**Capabilities 默认集**（最小权限）：
- `read_issue` / `write_evidence` / `write_artifact_meta`
- `signal_progress` / `signal_blocked`
- ❌ 绝不含 `proxy_provider_credential` / `modify_squad` / `invoke_other_agent`

#### 2.4.4 macOS Keychain 集成

- 真实 Provider 凭证存在 Keychain（Service=Loom，Account=user-supplied）
- daemon 启动时通过 Security Framework 拉取，**仅在内存持有 + mlock 防止 swap**
- 任何 CLI 进程**不直接接触** Provider 凭证；都通过 DaemonToken 走 daemon 代理

### 2.5 MCP 适配

#### 2.5.1 现实约束（来自 Multica 11-CLI 矩阵）

Multica 明确承认：14 家适配的 CLI 中，**只有 Claude Code 真正消费 MCP 服务**。其余 13 家或不支持，或仅部分支持。

**v2.0 决策**：**Broker 模式**，不自实现 MCP server / client 协议。

#### 2.5.2 Broker 模式

```
MCP Server (用户/registry 提供)
  │  stdio / SSE
  ▼
Loom MCP Broker（daemon 内置组件）
  │  验证 server 身份 + 能力声明 + 沙箱挂载
  │  转换协议到 v2.0 内部受控格式
  ▼
RuntimeAdapter（按 CLI 能力裁剪）
  │  只对 mcp_consumer=true 的 CLI 下发
  ▼
Claude Code（以及其他未来支持 MCP 的 CLI）
```

#### 2.5.3 v2.0 范围

- **实现**：MCP Broker 协议转换 + 能力过滤 + 沙箱挂载
- **不实现**：MCP server 注册中心（v2.0 直接读 `mcp.json` / `~/.mcp/config.json`）
- **不实现**：MCP 多租户（单用户单 daemon，Broker 是本地进程）
- **依赖**：Anthropic MCP SDK（Go port 已有 `mark3labs/mcp-go`，2.1k stars）

#### 2.5.4 风险与回滚

如果 Claude Code 之外有 ≥3 个 CLI 在 v2.0 发布前原生支持 MCP，**升级 v2.1 全面 MCP**；否则保持 Broker-only。

## 3. Sandbox 层 — kvcache-ai/AgentENV

### 3.1 为什么选 AgentENV

kvcache-ai/AgentENV 是 Moonshot AI 为 Kimi K3 agentic RL 训练自研的分布式沙箱平台：

- **Firecracker + OCI 镜像** + overlaybd 按需加载（本地磁盘做 bounded cache）
- **<50ms 启动/恢复**，<100ms 暂停，快照分叉 <100ms
- **MIT 协议**（v2.0 集成无许可问题）
- **E2B 兼容 HTTP API**（关键 — 不需 fork 它的代码，直接用 E2B SDK）
- 2.7k stars / 209 forks / 已被 Moonshot 内部生产验证

### 3.2 E2B 兼容 API 集成模型

AgentENV 暴露 E2B 兼容 HTTP API，意味着 Loom 可以用 **官方 E2B SDK** 调它：

```python
# 概念示例（v2.0 实际在 Go 里用 E2B Go SDK / HTTP client）
import os
os.environ["E2B_API_URL"] = "http://127.0.0.1:8000"   # 本地 AgentENV server
os.environ["E2B_API_KEY"] = "e2b_<daemon 启动时生成>"

from e2b import Sandbox
sb = Sandbox.create("loom-base")          # 模板名
result = sb.commands.run("echo hello")
sb.beta_pause()                            # 暂停（<100ms）
# 之后可 resume
```

**Loom 集成点**：
- `internal/sandbox/agentenv_client.go`（v2.0 新增）— AgentENV HTTP client
- `internal/sandbox/template_registry.go`（v2.0 新增）— OCI 模板缓存
- `cmd/loom/sandbox.go`（v2.0 新增 CLI）— `loom sandbox start/pause/resume/list/delete`

### 3.3 沙箱生命周期映射

| AgentENV 命令 | Loom 调用时机 | 用途 |
|---|---|---|
| `aenv pull <oci>` | 首次注册 Skill/Agent 时 | 预热模板 |
| `aenv start <tmpl>` | Task dispatched 时 | 创建执行沙箱（<50ms） |
| `aenv exec <sb> <cmd>` | Agent 进程内 Tool Call | 单次执行 |
| `aenv pause <sb>` | Issue 转入 Blocked 状态 | 节省资源（<100ms） |
| `aenv resume <sb>` | Issue 解除 Blocked | 恢复现场 |
| `aenv timeout <sb> 600` | Task 临近 deadline | 续命 |
| `aenv delete <sb>` | Task 终态后 5 分钟 | 清理 |

### 3.4 aenv CLI 包装

v2.0 不直接让 Agent 调 aenv；走 Loom daemon 中转：

```
Agent 进程 → RunToken 调 daemon 能力
         → daemon 内部 sandbox service → AgentENV HTTP API
         → 返回结果给 Agent
```

理由：Agent 不应直接知道 AgentENV 存在（关注点分离 + 安全审计点）。

### 3.5 不强制使用 AgentENV 的回退路径

- v2.0 早期（Phase 2.A）：AgentENV 作为**可选项**；用户未启动 AgentENV 时，Loom 回退到 v1.x 的"无沙箱"模式（仅进程隔离 + cgroup）
- v2.0 后期（Phase 2.D）：AgentENV 成为默认；用户禁用需显式 `--no-sandbox`

### 3.6 AgentENV 与 v0.3 Runtime 关系

v0.3 的 `RuntimeInstance` 是"外部 CLI 进程 + Loom 监督"；v2.0 的 `SandboxInstance` 是"Firecracker VM + AgentENV 监督 + Loom 监督"。两者**并存**：

- **ExternalRuntimeInstance**（v0.3 沿用）：用于本地用户直接调起的 Claude Code / Codex
- **SandboxedRuntimeInstance**（v2.0 新增）：用于 Loom Squad 自动调度的 Agent

选择规则在 `internal/runtime/router.go`（v2.0 新增）：Squad Issue 优先 Sandboxed；用户显式 external 走 External。

## 4. 数据模型迁移

### 4.1 WorkItem → Issue + Task 拆分（来自 Multica #25 经验）

v0.3 的 `WorkItem` 单一实体承载"问题"+"执行"两重身份，复杂度高。v2.0 拆为：

```yaml
Issue:                              # 用户的"做什么"
  id: iid_<8hex>
  squad_id: sqd_<8hex>
  title: "string"
  body: "string"
  context_refs: list[string]        # JSONB；指向 Workspace.context
  acceptance_criteria: list[string] # JSONB
  status: enum{open, in_progress, blocked, review, done, cancelled}
  created_at, updated_at
  policy: enum{one_to_one, one_to_many, fanout}

Task:                               # Issue 的一次具体执行
  id: tid_<8hex>
  issue_id: iid_<8hex>
  agent_ref: AgentRef
  runtime_instance: RuntimeInstanceRef
  status: enum{queued, dispatched, running, ready_for_review, terminal_failure, terminal_success, terminal_cancelled}
  attempt: int                       # 重试计数
  parent_task_id: tid_<8hex>?        # 重试时指向上一次
  session_id: string                 # 继承关系锚点
  timeout_ms: int                    # 默认 2.5h
  dispatched_at, started_at, terminal_at
  evidence_refs: list<artifact_id>
```

**核心变化**：
- `Issue` 1:N `Task`（重试 / 并行都自然）
- `Task.status` 才有 `dispatched/running/...` 这种运行态；`Issue.status` 只有 `open/in_progress/...` 这种问题态
- `Task.session_id` 是 Multica session 继承机制的关键（手动 rerun 不继承 → 起新 session）

### 4.2 新增 Skill 实体

见 §2.1.1。

新增表 `skill` + `skill_version` + `skill_mount_audit`（ClawHavoc 防御审计）。

### 4.3 新增 Squad 实体

见 §2.2.1。

新增表 `squad` + `squad_member` + `squad_skill_binding` + `routing_rule`。

### 4.4 3-Token 持久化

| Token | 存储 | 校验 |
|---|---|---|
| UserToken | 内存 + mlock（daemon 进程） | 每次 API 调用 ed25519 验签 |
| DaemonToken | daemon SQLite `daemon_token` 表 | TTL 30 天，滚动刷新 |
| RunToken | daemon SQLite `run_token` 表 | TTL 5 分钟（最长 1h），Task 终态吊销 |

### 4.5 迁移路径

v0.3 → v2.0 数据迁移脚本（`cmd/loom/migrate/v1_to_v2.go`）：

1. `WorkItem` 拆分为 `Issue` + `Task`（一对一初始；多 Task 关系后期重连）
2. `AgentDefinition` 不变；`Squad` 从 `Team` 派生
3. `Credential` 表新增 `token_kind` 列
4. `Event` 表新增 `squad_id` / `issue_id` / `task_id` 三列（nullable，向后兼容）
5. 老 `WorkItem` 表保留 90 天只读；新写入走 Issue/Task

## 6. 风险与回滚

| # | 风险 | 概率 | 影响 | 缓解 | 回滚 |
|---|---|---|---|---|---|
| 1 | AgentENV 启动复杂（docker compose + K8s） | 中 | 中 | Phase 2.D Day 1 用 docker compose 验证；提供 `aenv-up.sh` 一键 | `--no-sandbox` 回退 v1.x |
| 2 | E2B SDK 在 macOS 上有原生依赖 | 低 | 中 | 备选 HTTP client 直连 AgentENV（不用 SDK） | 切 HTTP client |
| 3 | WorkItem 拆分破坏现有 run 状态机 | 高 | 高 | Phase 2.B Day 3 强制 fresh reviewer；保留 90 天 v1 WorkItem 只读 | 90 天内可回退到 v1 WorkItem 路径 |
| 4 | ClawHavoc 类似事件（用户自己写危险 Skill） | 中 | 高 | Skill 4 源限制 + `scope=local` 默认 + `mounts` 显式声明 | 紧急关闭 `scope=workspace` |
| 5 | 3-Token 复杂度让 onboarding 变难 | 中 | 中 | 提供 `loom auth wizard` 一键 | 老路径保留 30 天 |

**触发回滚的硬条件**（任一满足 → 立即停止 v2.0 推进，回退到 v1.x）：
- AgentENV Phase 2.D Day 4 仍无法与 Task 状态机对接
- 3-Token Phase 2.C 引入安全 bug（fuzzing 发现）
- Issue/Task 拆分导致 v1 数据迁移丢失 > 0.1% WorkItem
